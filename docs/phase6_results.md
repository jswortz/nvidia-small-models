# Phase 6: Training the Router

The routed agent already scored 62 of 62 on the eval set, so the question for this phase was narrower: how much better can the one model call that matters most, the router, get on messages it has never seen, and what does it take to get there with NVIDIA's training stack?

## What I measured

The router turns a customer message into five fields: intent, order number, damaged, photo provided, and the product they want instead. I scored it alone, field by field, on two sets I built for this phase:

- **Dev, 83 messages**, written in the same three styles as the training data (polite, casual, frustrated).
- **Stress, 147 messages**, written in three styles the training data never used: non-native English with typos, long rambling messages, and terse phone shorthand. These come from separate specs and separate orders, so nothing in stress overlaps training.

A route counts as exact when all five fields are right. I also ran every route through the store-state reward to count harmful routes: routes that would make the store change something the correct route would not. The 62-case eval set and the 11 held-out cases were never used for training and stay as the final regression check.

## Results

| Router | Prompt | Dev exact | Stress exact | Harmful routes |
| --- | --- | --- | --- | --- |
| Base Nano 9B | Full (what the agent used) | 56/83 (67%) | 114/147 (78%) | 0 |
| Base Nano 9B | Short | 72/83 (87%) | 126/147 (86%) | 0 |
| LoRA SFT | Short | **83/83 (100%)** | **144/147 (98%)** | 0 |
| LoRA SFT + GRPO | Short | not completed | not completed | not completed |

Three things stand out.

**The long prompt was hurting.** Before training anything I ran the base model with a one-line prompt as a control. It beat the carefully written prompt by 8 to 20 points, almost all on the product field. The full prompt asks for the new product "in their words," and the model took that as license to paraphrase, which then failed the product search. I would not have found this without the control, and it changes how I read the SFT gain: the fair baseline is 86% on stress, not 78%.

**Fine-tuning closed most of the remaining gap.** SFT took stress from 86% to 98% exact and dev to 100%. It also uses the short prompt, so each router call sends about 350 fewer prompt tokens than the agent does today.

**No router ever produced a harmful route.** Across 690 scored routes in six runs, every mistake would have left the store unchanged or matched what the correct route would do. That is the design doing its job: the policy engine and the tools catch what the router gets wrong. Training improved accuracy, and safety was already there.

The three SFT misses on stress: a rambling policy question read as "other," a multi-order message where the customer wanted a replacement but the router said refund, and a terse message where the router named a product the customer never asked for. None would change the store.

## How it was trained

- **Data:** 676 training messages generated by hosted Nemotron Super from 265 specs, with labels coming from the spec rather than the model, so they are correct by construction. Automatic checks dropped 132 messages that broke their brief, duplicated another message, or overlapped the eval sets, and 9 specs returned nothing usable.
- **Method:** LoRA SFT with NeMo AutoModel, starting from NVIDIA's `nemotron_nano_9b_squad_peft.yaml` recipe. Rank 16, alpha 32, learning rate 1e-4, batch 16, 160 steps. Mamba `out_proj` layers are excluded, as in the recipe.
- **Selection:** dev loss picked the checkpoint at step 128.
- **Hardware and cost:** one A100 80 GB on Brev at $1.62 per hour. Training took 4 minutes. Peak memory was 18.3 GB, so the same run fits on my 24 GB 3090 with the model server stopped.
- **Serving:** the adapter is merged into the base weights and served by the same vLLM v0.10.1 image the agent already uses.

## GRPO

The setup: NeMo RL v0.7.0, starting from the SFT model, LoRA, 16 messages times 8 sampled routes per step, rewarded by the final store state (+1.0 for the right state, -2.0 for a harmful change, +0.25 for an exact route, +0.1 for valid JSON). My expectation going in was a small gain at most, because SFT already earns the maximum reward on dev.

It did not finish a single training step. The limit was host memory, not the GPU. NeMo RL keeps a training copy of the model and a vLLM copy for sampling, and while loading, the training copy briefly used 53 GB of RAM because it loads in float32. With vLLM's 29 GB on top, that was too much for the instance's 94 GB. Ray killed the second attempt at 95%. For the third, I added 64 GB of swap and turned off Ray's memory monitor. The model loaded and the starting validation ran, but the first training step filled RAM and swap, and the machine stopped responding. I stopped there and deleted the instance rather than keep paying for retries. Running this properly needs a node with roughly 200 GB of host RAM, or a setup that does not hold two full copies of a 9B model in host memory.

The starting validation still taught me something. Sampled freely at temperature 1.0, without the JSON schema that vLLM enforces in the live agent, the SFT router wrapped 73 of 83 answers in a markdown code fence. The strict reward scores those as 0, so the mean was 0.16 out of 1.35, even though the routes inside the fences looked right. The agent is unaffected because it always decodes with the schema. But it shows that 100% under guided decoding does not mean the model learned the bare format, and it is exactly the kind of gap GRPO would have closed first.

## Problems worth knowing about

- AutoModel needs the complete model snapshot in the Hugging Face cache, not only the weights. The first start failed on this before using any GPU time.
- AutoModel's merge tool merged correctly but could not save Nemotron Nano under the newer `transformers`, because the model's custom code stores tied weight keys as a list. I wrote a merge that works on the weight files directly and copies everything else unchanged, which also guarantees the result loads in older vLLM.
- The base model with the short prompt sometimes returned `true` for the product field. The router now accepts only text there. The live agent would have crashed on it.
- The reward function pointed product search at a temporary store it had already deleted. A replacement case with a product name exposed it; there is now a test for it.
- NeMo RL's GRPO config inherits keys from the example it extends, so the dataset name and the LoRA `match_all_linear` default had to be overridden explicitly. Both failed fast and cost little.
- On Brev, `brev exec` holds the session open when it starts a background job. Plain `ssh -T` with the config Brev writes is faster and does not hang.
